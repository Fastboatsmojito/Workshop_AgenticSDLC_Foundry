# Take-home 5 — Evaluation in CI (~60 min)

Right now the only judge of agent quality is a human at a gate. That does not
scale, and it means a one-word change to an instruction can quietly make things
worse with nothing to catch it.

## What is worth measuring

Not "is the output good". Specific, checkable properties:

| Property | How to check it | Why it matters |
|---|---|---|
| **Citations are real** | Every `doc_id` + `section` exists in the corpus | A fabricated citation is worse than none — it survives review |
| **Citations are relevant** | The cited section actually supports the claim | Real-but-irrelevant citations are the subtler failure |
| **Requirements are testable** | No "fast", "robust", "user friendly" without a threshold | The DoR requires it (DoR-04) |
| **DoR honesty** | Assessment matches a human label on known-weak initiatives | Catches the model's agreeableness |
| **Escalates when it should** | `INIT-9001` asks; `INIT-1042` does not | Both directions, or you over-correct |
| **Schema validity** | The artifact parses | Free — you already have it |

The first and the fourth are the ones that catch real regressions.

## Step 1 — Start with what needs no model

Citation checking is deterministic. Write it first:

```python
# tests/test_evaluation.py
from agentic_sdlc.config import DATA_DIR
from agentic_sdlc.grounding.ingest import load_corpus

def known_sections() -> set[tuple[str, str]]:
    return {(c.doc_id, c.section) for c in load_corpus(DATA_DIR / "corpus")}

def test_every_citation_points_at_a_real_section(saved_requirements):
    known = known_sections()
    for citation in saved_requirements.citations:
        assert (citation.doc_id, citation.section) in known, (
            f"fabricated citation: {citation.doc_id} §{citation.section}"
        )
```

This runs offline, in milliseconds, and catches the highest-consequence failure
mode. Do not skip past it to the interesting model-graded work.

## Step 2 — Build a small labelled set

`data/evaluation/cases.json`, hand-labelled. Ten cases is enough to be useful:

```json
{
  "cases": [
    {
      "initiative_id": "INIT-1042",
      "expect_dor_failures": ["DoR-03", "DoR-08"],
      "expect_open_questions_about": ["eligibility threshold", "retention period"],
      "expect_clarification": false
    },
    {
      "initiative_id": "INIT-9001",
      "expect_clarification": true,
      "note": "Under-specified. Asking is the correct behaviour."
    }
  ]
}
```

Label these yourself. A labelled set someone actually thought about beats a
larger one generated by a model, because the disagreements are where you learn
what your instructions really say.

## Step 3 — Add model-graded checks

Some properties need judgement: does this citation support this claim, is this
acceptance criterion genuinely testable. `agent_framework.foundry` provides
`FoundryEvals` and `evaluate_traces` for scoring runs.

Two rules that save a lot of pain:

**Grade one property at a time.** A grader asked for an overall quality score
returns noise. A grader asked "does the cited section support this specific
claim, yes or no" returns something you can act on.

**Calibrate against your own labels.** Run the grader on cases you labelled by
hand. If it disagrees with you more than occasionally, fix the grader before you
trust it on anything else.

## Step 4 — Wire it into CI

```yaml
# .github/workflows/evaluate.yml
name: Evaluate agents
on:
  pull_request:
    paths:
      - 'src/agentic_sdlc/agents/**'
      - 'data/corpus/**'

jobs:
  offline:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11' }
      - run: pip install -r requirements.txt && pip install -e .
      - run: python -m pytest -q          # contracts, gate, corpus, mocks
```

Note the `paths` filter. **Instructions are code.** A change to
`requirements_agent.py` should trigger evaluation exactly as a change to the gate
triggers the gate tests. That framing — prompts under the same review and
regression discipline as everything else — is most of the value of doing this at
all.

Add a second job with Azure credentials for the live evaluation, and require the
offline one on every PR.

## Step 5 — Track it over time

Store each run's scores keyed by commit. What you are looking for is not the
absolute number but the direction: the day someone tightens an instruction and
DoR honesty drops four points is the day this pays for itself.

## Exercises

**A. Adversarial initiatives.** Write inputs designed to make agents behave badly:
contradictory constraints, a requirement that violates the architecture
standards, an initiative that is actually two initiatives. Add them to the set.

**B. Regression-test the gate.** Assert that a tampered artifact always fails
`verify`. You have this in `tests/test_approval_gate.py`; make it a required
check so nobody can weaken the property without noticing.

**C. Cost and latency budgets.** Track tokens and wall time per stage. Fail the
build if a change makes the Requirements Agent twice as expensive for no
measurable quality gain.
